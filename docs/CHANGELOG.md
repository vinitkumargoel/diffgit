## T11.11 — Home dashboard: repository summary cards (2026-09-19)

- **Home's Recent list became the RepoCard grid** (Design §14.6, atlas tab 11). Each card is the RecentRow facts plus the repository's own state: name with the access dot, the operation tag (`rebase 2/3`), the current branch and `4 ↑ 0 ↓` vs upstream, the uncommitted work as counted `LayerChip`s (`5 staged`, `2 conflicts`) or `clean`, the last commit's age, and `Open` / `Re-authorise` / Forget. Nothing was added to the app's chrome — this is the landing page's own hero column, `RecentRow` is untouched and still serves the nav popover (H5), and the Continue card (H1, exactly one repository) shows the same summary strip so a single stored repository is not the poorer card. `LayerChip` gained an optional `count`; `RecentRow.Highlight` is now exported so the filter still marks matches (H3).
- **The dashboard never blocks opening a repository.** Every card renders from `diffgit-derived` (`summary:<repoId>`) before anything is read; only then are the repositories walked, **one at a time** (`SUMMARY_CONCURRENCY`), each through `engineClient.summaryClient()` — a second, short-lived `WorkerClient`: `open` → `summarise` → `close` → `terminate`. The open repository keeps its generation, caches and packs (contracts `<!-- T10.10 -->`), and the atlas's memory note ("close each session after the summary") is literally what the `finally` does. `HomeScreen` starts the sweep in an effect and cancels it on unmount; `pickAndOpenRepo` and `useRecents.open` cancel it before the gesture; every step checks the sweep's ticket, so a summary already in flight lands nowhere.
- **The FSA permission model is respected.** `queryPermission()` comes first and only `granted` handles are summarised — `requestPermission()` needs a user gesture, and twenty prompts on load is the atlas's first risk. A `prompt` or `denied` card is dashed, wears `needs permission` and offers `Re-authorise`, which calls `ensurePermission` **inside the click and nothing else**: granting is not opening, and the card fills where it stands (the permission answer changes, the sweep restarts and skips everything already fresh).
- **Revalidation is the index mtime, read by the UI.** New `indexMtimeOf(handle)` reads `<repo>/.git/index`'s `lastModified` straight off the directory handle — the same number `IndexReader` keys `RepoSummary.indexMtimeMs` on — and a repository is re-read only when the two disagree; `Refresh all` (in the panel header, not the app's chrome) skips the check. `isStale(entry)` is exactly that disagreement and is the atlas's stale marker, so a card that is behind the working tree and cannot be refreshed says so while still showing what it knows.
- **Decisions / deviations.** (1) **No `EngineApi.statIndex`**, although the task allows one: every engine entry point opens a session first, which is the cost the check exists to avoid; one file handle in the UI answers the same question, and the engine, the worker and the recordings stayed untouched. (2) **`closeRepo` does not clear the slice** (unlike every other v2 slice): the dashboard is Home's state, not an open repository's, so closing only bumps the sweep's ticket — a summary read a minute ago is still the right thing to show while the next one is read, and the mtime check re-reads whatever moved. (3) **The `worktree` fixture has no recorded `vsUpstream`** — no fixture does, because none has a remote — so the ahead/behind pair (and its capped `≥`) is asserted by rendering `RepoCard` with a constructed `AheadBehind`, reusing T11.7's `aheadBehindLabel` / `CAPPED_TITLE` / `NO_UPSTREAM` so the app has one vocabulary for divergence. (4) `RepoSummary` carries the counts but **not the upstream's name**, so the card prints `4 ↑ 0 ↓` with a title naming the upstream rather than the atlas's `4 ↑ 0 ↓ main`; adding the name is an engine change (`RepoSummary.upstream`), noted as a follow-up. (5) A summary with no `lastCommit` prints **nothing** instead of "no commits yet": the line is about the summary, not a claim about the repository. (6) `Refresh all` lives in the grid's header only; the Continue card keeps its four actions and re-reads itself on every visit. (7) `workerClient.mock.ts`'s `summarise()` fallback now derives its counts from the open recording instead of the last computed diff, so a fixture without a recorded `summary` (`worktree`, `basic`, the showcase sets) gives a card its real layers; `bun run record` is untouched and unchanged.
- New files: `src/ui/dashboard.ts` (the concurrency, the chip order, `operationTag`, `lastCommitLine`, `isStale`, `indexMtimeOf` and every string), `components/home/RepoCard.tsx`. Store: `dashboard: DashboardState` with `loadSummaries(repos, { force })` / `cancelSummaries()` and the `setSummaryClientFactory` test hook (contracts `<!-- T11.11 -->`).
- Tests: `dashboard.test.ts` (9 pure cases on the recorded summaries: the chip order and the zero filter on `secrets` / `hidden` / `rebase-conflict` / `history`, the plurals, the one-at-a-time constant, `rebase 2/3` vs a bare `merge`, the last-commit line and its null, `last seen on`, the four staleness cases, and `indexMtimeOf` against a handle, a marker, a throw and a gitdir file) and `components/dashboard.test.tsx` (16: the `worktree` counts and the `rebase-conflict` operation card, `clean` + `no upstream` on `history`, ahead/behind and its capped form, axe in both themes, a cached card rendered with no session at all, three repositories read in order with one live session and three terminations, the write-back to `diffgit-derived`, the skip-on-matching-mtime and the re-read when it differs, the stale marker on a card that cannot be refreshed, `Refresh all`, `Re-authorise` filling a card without leaving Home, cancel on unmount with no spinner left, a `HANDLE_GONE` card that says "Folder not found" while its neighbour fills, and the store's own empty list / cancel / open-wins cases).

## T11.8 — Search in the palette: commits, files, content, pickaxe (2026-09-19)

- **The palette is the whole surface** (Design §14 rule 2, atlas tab 05). Nothing was added to row 1 or the StatsRow: `⌘K` and a prefix is the entire feature. `>` searches commits (message, author, and a 4–40 hex object name as a SHA lookup), `grep:` the working tree, `-S` the pickaxe; `msg:` is accepted as the atlas mockup's spelling of `>`. `regex:` straight after the prefix sets `SearchRequest.regex` — without it the query is a literal substring and the engine builds no pattern at all, so `(a|b)*` is text. With no prefix the box is the command list T11.1 built, unchanged; the three `Scopes` rows are offered only on the *empty* box, where they cannot out-score a command for the highlighted row, and a footer line names the grammar at all times.
- **Results are cmdk rows**, so the arrow keys, Enter and the focus trap were already right. They are grouped under a heading that carries the count (`Working tree · 8 matching lines`), each row printing what the contract gives it: a short SHA in `--accent` plus the subject for a commit, `path:line` plus the line's text for a file, and the pickaxe's `delta` as `+5 occurrences`. Enter does what the hit *is* — a commit selects itself in History mode (`showCommit`), a file opens its card in Files mode and scrolls to the line through T11.9's `requestScrollTo(id, line)`, and the pickaxe's one hit with no `oid` (`Uncommitted changes`) is the working tree, i.e. Files mode. A grep hit for a path outside the current comparison has no card, so it says so in a toast instead of jumping nowhere.
- **The cost is a line, never a banner.** `scanned`, the duration and — when `capped` — one `--attention` sentence sit inside the list, and `SEARCH_CAPPED` joins `OPERATION_IN_PROGRESS` / `BLAME_CAPPED` / `SECRETS_FOUND` in the codes `WarningBanners` filters out: the answer is partial for exactly one search, and a repository-level banner would outlive it. The pickaxe always says what it scanned and offers `Widen ×5 to 1,000 commits`, up to 5,000 — its own keyboard row, not a link.
- **Store** (`docs/v2-contracts.md` `<!-- T11.8 -->`): one contiguous `search: SearchState` slice with `runSearch`, `widenSearch` and `cancelSearch`. `limit` is always 200; `path` is the **path part** of the file filter (`parseFilter` — `status:` / `layer:` are the sidebar's vocabulary, not the engine's) and is omitted when empty; `commits` is sent only for the pickaxe, where the contract makes it mandatory. `regex` is omitted rather than sent as `false`, so the request matches the `searchKey(req)` the recordings are filed under. Input is debounced 200 ms, every call takes a ticket so a newer query supersedes the older answer, and `STALE` / `CANCELLED` go through `ignoreStale`. T11.5's `searchCommits` is left alone: it answers the History list's own box with oids, which is a different question.
- **Decisions / deviations.** (1) The engine exposes no `cancelSearch`, so `Escape` on a running search *abandons* it — the ticket makes the reply land nowhere — and drops the box back to the bare prefix, so the second `Escape` closes the palette exactly as before. (2) Results render only while the slice describes exactly what is in the box, so a pending debounce never shows the previous query's hits under a newer one. (3) `recent queries` (parent brief) are **not** implemented: the task file's Deliverables do not name them and `derived.ts` has no key for them; noted here rather than invented. (4) Both `>` and `msg:` are accepted because the task file and the atlas mockup spell the commit scope differently; only `>` is advertised.
- New files: `src/ui/search.ts` (the prefix grammar, the request sizes and every string) and `components/paletteSearch.test.tsx` (17 cases on the recorded `history` fixture: the grammar, the widen ladder, the footer and the Scopes rows, the three scopes' exact `SearchRequest`s against the recorded `searchKey`s, a SHA prefix, a hit opening a card at its line, the capped line with no banner, the path-scoped grep, the pickaxe delta and widen, the empty answer, an uncompilable regex, `Escape` cancelling then closing, a superseded query, closing forgetting the search, and axe in both themes). No engine, mock or recording change was needed — T10.8 already records `searches` and runs the commit scope live.
- Checks: `bun run check` green — tsc, Biome (346 files), 718 engine tests (44 files), 626 UI tests (42 files), guards.

Both groups are measured against the ranked maximum, as the mockup draws them. The engine has no clock in this call — `activity` deliberately ends at the week of the newest commit (contracts T10.9) — and the derived key carries only tip + period, so a clock anchor would quietly change what a cached `90 d` means, and an idle repository would answer with an empty page. (2) `INSIGHTS_CAPPED` is printed as **one inline line** under the footer, driven by `InsightsResult.capped`; `loadInsights` dismisses the engine's one-shot warning so the same fact does not also take a banner (T11.6's `BLAME_CAPPED` rule), and `WarningBanners.tsx` was not touched. (4) `INSIGHTS_LIMIT` is **12** per group rather than the recording's 25: the engine answers "top `limit` files, then top `limit` manifests", and twelve bars is the length the atlas's ranked list reads at without the page becoming a wall of bars. (5) The heat of a day is its count's **rank among the distinct counts** spread over the five steps (`blame.ts`'s rule for age), not a quintile over the days: the recorded `history` repository commits at most once a day, and a quintile would paint every busy day the same whatever the ramp did. (6) The atlas's fourth panel, the "line age of the open file" strip, is **not** built here: it is a blame product (its own note says "needs blame (tab 02)"), the task's Deliverables do not name it, and T11.6 already draws that ramp in the card. (7) `ModePlaceholder.tsx` was deleted: its own doc comment scoped it to "T11.1 only; T11.5 / T11.7 / T11.12 replace each view", and this was the last mode using it.

## T11.7 — Branches mode: overview, ahead/behind, tags (2026-09-19)

Ahead/behind cells are the mockup's own 60 px two-colour bar (`--success` ahead, `--danger` behind, 10 px per commit squeezed into 60) plus the numbers, with `pull` / `push` / `diverged` and `merged` as `ref`-style tags whose titles say what git would do — never a button, because diffgit cannot write (D16). Cells are lazily filled: `branchOverview()` hands back rows with the expensive cells null, the visible rows queue in the store and one drain loop asks `branchCells` in batches of 50, exactly as `requestCommitStats` does for the commit list. Clicking a row (or Enter) walks that branch in History mode; `j` / `k` move between rows. Both tables are `role="grid"`.
- **Row `…` menu**: `Set as compare`, `Set as base`, `Compare with <base>`, `Preflight rebase onto <base>` (disabled, `coming soon (T11.13)`) and `Copy name`. `MenuItem` moved out of `CommitCard.tsx` into `components/MenuItem.tsx` and gained `disabled` + `title`, so the CommitCard's menu and this one are one component.

It reads `StoreState.tags`, which `loadPickerSources()` already narrows to `targetType === "commit"` (T10.5b), so a blob or tree tag is listed no more than `git log --all` walks it.

- **Decisions / deviations.** (1) **The base branch is not a preference of its own.** `selectBranchBase` reads the base side of the pickers while it is a plain ref (T11.5's `compareBase`, seeded by `openRepo` from the remembered `lastTarget` and moved by `Set as base`) and otherwise the repository's default branch — `RepoRef.isDefault`, which the engine resolves per D8 (`refs/remotes/<remote>/HEAD`, then `main`, then `master`). It is therefore chosen once and remembered per repository through the mechanism that already remembers the compare pair; a second `Prefs` key would have had to be kept in step with `lastTarget` for no gain. (2) **The `vs base` column is `branchCells.vsDefault` and its header prints the default branch's name** (`vs main`, which is what the atlas mockup itself shows). `BranchRow` carries exactly two comparisons and `branchCells` computes the second against `RefSnapshot.defaultRef`; asking `aheadBehind(base, branch)` per row for an arbitrary base is a second, uncached walk per row that the task's own deliverable ("`branchCells` for visible rows, 50 at a time") does not name. When `Set as base` has moved the base, the column still says `vs <default>` and the menu says `Compare with <base>` — each label names the branch it actually used, so no number is printed that was not computed. (3) `AheadBehind.capped` renders as a `≥` prefix on **both** counts (`≥4 ↑ ≥0 ↓`) with a title quoting the 10,000-commit cap: T10.5b makes both counts lower bounds once the walk is capped, so prefixing only one would be a guess. (4) **Tags are ordered by name, numerically aware** (`v1.10.0` above `v1.9.0`), because git gives a lightweight tag no date of its own; the Age column shows a tagger date for an annotated tag and `—` with the reason for a lightweight one, and `Compare with <prev>` names the tag it will use rather than leaving "previous" implicit. (5) `Preflight rebase onto base` is **listed and disabled** rather than hidden, per the owner's rule recorded in T11.5, although the task text says "hidden until then". (6) **`HISTORY_DEGRADED` is driven by the rows, not by the warning**: `branchOverview` hands back a row with `lastCommit: null` for a tip it could not read, and `recompute()` replaces `warnings` with the diff's own on the next refresh, so the page counts those rows and prints one inline line above the table (plus `—` with the reason in the row itself) instead of depending on a warning that does not survive. (7) The two tables keep a native `<table role="grid">` with one file-level Biome suppression: the rows really are focusable grid rows, and Biome's alternative (a `div` tree) costs table layout and demands a focusable wrapper per cell for nothing.

## T11.9 — Secret findings: banner, in-card markers, reveal (2026-09-19)

- **The secret scan is a contextual surface, never a mode** (Design §14.2 / §14.3, atlas tab 14). `WarningBanners` gained `SecretBanner`, a danger-level row that exists only while a finding does: `4 possible secrets in uncommitted changes. They are in the working tree, not committed yet…` with two accent links. `Show` opens the finding list **and** jumps to the first file and line; each row is `rule · path:line · masked` and jumps to its own card and line. `Rules` opens a popover with the rule-set date, what the scan actually looked at, and the two allowlists (`# diffgit:allow-secret`, `.diffgitignore-secrets`). Nothing was added to TopBar row 1 or the StatsRow; the only new palette entry is `Re-scan for secrets`.
- **In the card**: the flagged line gets a 3 px `--danger` left rule (`generateLineClassName` → `.dg-secret-line`) and a react-diff-view **widget row** under it carrying the marker — rule name in the `--chip-conflict` palette — which opens `SecretPopover`: line, rule, entropy in bits/char, where the value is (`staged in the index` / `working tree only`, never "in a commit"), why it was flagged, the allowlist help, `Reveal`/`Mask`, and `Copy rotate checklist`. Widgets are registered under every key shape a change can produce (`k`, `00k`, `k00`, `kk`), so the marker survives the `Unified | Split` switch. The sidebar row wears a `secret` chip after the XY layer code.

## T10.11 — Bisect stepping and rebase preflight (2026-09-19)

- New `src/engine/git/bisect.ts` (`revListOrder`, `bisectStep`) and `src/engine/git/preflight.ts` (`rebasePreflight`, `PREFLIGHT_COMMIT_CAP` 500, `ADJACENT_LINES` 1). `BisectState`/`BisectStep`/`PreflightRow`/`PreflightResult` are in `types.ts`; `EngineApi`, `RepoSession`, `workerApi` and `WorkerClient` gained `bisectStep(state)` and `rebasePreflight(branchRef, ontoRef)`, both single-in-flight, abort-aware and read-only (D16 — the checkout and the rebase stay the user's commands).
- **Bisect follows `bisect.c`.** Candidates are `git rev-list <bad> ^<good…>` in git's date-priority order; `find_bisection` reverses that list before weighing, so the scan is oldest-first and a tie goes to the older commit — which is why `git rev-list --bisect` over the 59 commits of `history` answers weight 29, not weight 30, both scoring `min(w, 59 − w) = 29`. Weights are git's three passes (roots, `count_distance` per merge, `weight(parent) + 1` along single-parent strands) and the pick is the largest `min(weight, remaining − weight)`. Two documented divergences: git's `halfway()` short-circuit is not replicated (it always returns a commit of maximal distance, but a merge-heavy tie could pick a different one), and `skipped` commits are removed from the *count* per the brief instead of git's PRNG replacement (`get_prn`, not reproducible from outside) — they stay in the graph, never come back as `candidate`, and count for nothing.
- **Preflight grades per commit, not per tip.** The brief said "`computeHunks` of each side vs the merge base", which is per path at the two tips and contradicts the fixture: `preflight/a`'s p2 keeps p1's edit to the top of `src/hot.txt`, so tip-vs-base ranges grade it `likely` while the real `git rebase --onto main p2^ p2` recorded in `expected/preflight-outcome.txt` applies it cleanly. Each side is therefore read as the patch a rebase replays (commit vs its first parent), old-side ranges from `computeHunks(context: 0)`: overlapping/adjacent (≤ 1 line) → `likely`, same file disjoint → `possible`, untouched path → `clean`, row = worst. Binary blobs and gitlinks changed on both sides are `likely`; an unreadable or > 10 MB side is `possible` plus `HISTORY_DEGRADED`. Renames map through `detectRenames` between the merge base and each tip. Written up in `docs/v2-contracts.md` under `<!-- T10.11 -->`.
- **Parity.** The bisect replay reproduces `fixtures/history/expected/rev-list-bisect.txt` oid for oid at all 7 rounds (59 → 30 → 15 → 8 → 4 → 2 → 1, first bad `822313f`). The preflight on `preflight/a` onto `main` answers `likely / possible / clean`, and the `likely` row is exactly the commit the recorded `git rebase` stopped on, with `src/hot.txt` as the conflicted path; `main` onto `preflight/base` finds the merge of `topic` and switches the command to `git rebase -i --rebase-merges`. `fixture-expectations.sh` gained `record_preflight_todo`, which captures the todo `git rebase -i` itself writes (throwaway clone, sequence editor copies the file out and exits non-zero, nothing replayed) — git ≥ 2.46 spells it `pick <sha> # <subject>`, so the test strips an optional `# ` and the engine emits the `pick <sha7> <subject>` form the contract fixes and every git parses.

## T10.5b — Walker review fixes (2026-09-19)

- **B1 (blocker):** a tag on a blob or a tree (git.git ships `refs/tags/junio-gpg-pub`, a blob) crashed `walkCommits({all})`, `markReachable` and `reflog` with isomorphic-git's `ObjectTypeError`. `ObjectDb.objectType` is new, `TagInfo` gains `targetType`, `CommitReader.meta` answers **null** for a non-commit, and the seeds/tips in `walkSeeds` and `reachableSet` skip anything but a commit — exactly what `git log --all` does. `fixtures/tags` gained `blob-tag` and `tree-tag`; parity is against `git log --all --format=%H` and `git tag -l --format`.
- **S1:** the streaming indegree emitted a parent before a child discovered later under committer-date skew and then reserved a lane for that emitted oid, leaking a column and leaving a dangling edge. The walk now does git's two passes over a **window** — `limit + LOOKAHEAD` (512) commits discovered and counted before anything is released — and `placeCommit` takes the emitted set so it can never reserve a lane for, or draw an edge into, a commit already gone. New `fixtures/skew` (built with `git commit-tree` and explicit `GIT_COMMITTER_DATE`s, a parent newer than its child) reproduced the bug; it now matches `git log --date-order` for HEAD, `--first-parent` and `--all` and satisfies `assertContinuous`. `docs/v2-contracts.md` states the guarantee honestly instead of claiming agreement in every case.
- **S2/S4:** `WalkPage.cursor` is now an opaque session token (`w<8 hex>.<n>`, 13 B) into walk state the session holds, not a JSON frontier of ~47 B per commit walked (~2.3 MB at the cap, ~1 GB over a paging run). A token the session does not hold, and one whose request key no longer matches, both reject with `STALE` — the contracts say the UI restarts the list; a cursor that is not a token at all is `INTERNAL` with the text as `detail`. `dropHistoryCaches()` clears the store, so refs moving invalidates every outstanding cursor instead of silently restarting page 1.
- **S3:** `aheadBehind` is git's own algorithm — one date-ordered queue seeded LEFT/RIGHT, COMMON painted where they meet, stopping on `still_interesting` — so it walks the divergence, not both full histories, and the counts are exact where the old two-truncated-sets version produced arbitrary numbers.
