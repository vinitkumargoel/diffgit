01 — Layers

What git status knows, in the diff.

Every other diff viewer stops at the last commit. diffgit reads the index and the working tree after the commits, and labels each file with the layer it came from. A file can be in two layers at once; both chips show, and the diff is the sum.

Untracked files respect .gitignore, .git/info/exclude and the built-in excludes. Conflicts and generated files are flagged the same way.

02 — Same maths as a pull request

Three-dot, from the merge base.

The diff is merge-base(base, compare) → compare, exactly what GitHub shows on “Files changed”. Commits that landed on main after you branched don't show up as your changes. Then the index and the working tree are appended as two more steps.

Renames are found like git diff -M: exact matches first, then 50 % similarity, and fixtures are checked against git's own output on every build.

03 — Live

Save in your editor. Glance at the tab.

Where the browser has FileSystemObserver (Chrome 129+) the folder is watched. Elsewhere, .git and the index are polled every two seconds. Only files whose size or mtime changed are re-hashed, with git's own racy-git rule for edits in the same millisecond as the index write.

Shift+R re-hashes everything, when you'd rather be sure than fast.

04 — Private by construction

Not a promise. A header.

The page can't phone home even if it wanted to. The served Content-Security-Policy forbids network connections from the page and its workers, and an end-to-end test asserts zero requests while a repository is open.

Source is public, the build id is in the help dialog, and the deploy script refuses to ship if the served commit doesn't match. Read the privacy model →

Questions people ask.

Why only Chromium browsers?

diffgit reads the folder through the File System Access API, specifically showDirectoryPicker(). Firefox and Safari don't ship it. On those browsers the home screen says so instead of failing later.

Is it really read-only?

Yes. The directory is opened with mode: "read", and the engine's filesystem adapter has no working write path: every write method throws. A mtime-based proof on real repositories is part of the release checklist.

Does it work on large repositories?

Over 300 changed files, the tree and diff pane virtualise and per-file stats stream in with the visible rows first. Files over 1 MB or 3,000 changed lines collapse behind “Load diff”. Packs over 1 GB, indexes over 200,000 entries and more than 5,000 untracked files are refused or capped with a named banner, never silently wrong.

What doesn't it support?

Linked worktrees, bare repositories, reftable, SHA-256 object format, partial clones and split index are refused or flagged with a code you can look up. Git LFS pointers are diffed as text. Copies (-C) are not detected. The full list is in the docs.

Does it replace GitHub's review?

No. It's the review you do before the pull request exists: the same diff, with the uncommitted work included, so what you push is what you meant to push.
