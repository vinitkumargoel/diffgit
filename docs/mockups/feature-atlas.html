What diffgit should build next

The goal is simple to state: nobody should download a git desktop app just to see their repository. diffgit already shows the branch diff. This atlas maps the nineteen viewing and guiding features that desktop GUIs still hold over it, each one computed from .git inside the browser, with a mockup, the numbers, and the risks.

What this consolidates

Two proposals existed for this question. The first atlas (18 September) ranked sixteen features with cited numbers. An earlier "Zero-Download Desktop" roadmap proposed twelve with interactive simulations and a metrics matrix, but its benchmark figures had no sources. This page keeps the atlas as the base, adopts three features from the roadmap that the atlas missed (secret scan, bisect helper, rebase preflight), adopts its matrix format in tab 21 with re-estimated numbers, and folds its better mitigations into the risk tables: packed typed arrays for the commit graph, bitset early termination for blame, bot filtering for churn, the empty-tree fallback for root commits, and a marker gate on exports. Its interactive rebase and conflict "resolvers" were not adopted as writes; their read-only halves survive as tabs 06 and 16.

What stays out, on purpose

  • Any write. Hunk staging is the single most-cited reason people open a GUI, and it is the one thing diffgit will not do. The read-only invariant (Plan D16, every write in the fs adapter throws) is the product's trust story. Exports below are downloads to a location the user picks, never writes into the repository.
  • AI summaries. Every competitor gates them behind a paid tier, and every one of them is a network call. connect-src 'none' is not compatible with that, and an in-browser WebGPU model still needs a first download. The honest differentiator is the opposite claim.
  • Native Firefox and Safari. Mozilla's position on the File System Access API is "negative", WebKit's is "oppose". Tab 15 covers the only degraded path that exists.

Limits that shape the proposals

  • Chromium desktop only. Needs showDirectoryPicker(). The BrowserGate explains this on other engines.
  • Refused layouts: linked worktrees opened directly, bare repositories, reftable, SHA-256 repositories, alternates, promisor clones, packs over 1 GB.
  • Size gates: index over 200,000 entries disables the worktree scan; more than 5,000 untracked files are capped; files over 1 MB collapse behind "Load diff"; over 10 MB never render.
  • isomorphic-git is used only as an object and ref reader. Its own index parser hard-throws on index v3/v4, which feature.manyFiles sets, so diffgit's own parser is load-bearing, not an optimisation.

How it works offline

File history

Walk commits from the chosen ref, first-parent by default, and for each one compare the path's blob id in the commit tree with its parent's. Only commits where the id changes are kept. When the path vanishes, run the existing rename detector between the parent tree and this tree to find where it came from, then continue on the old path. That is git log --follow.

Blame

Start with the newest content, diff it against the previous revision with the existing Myers implementation, and attribute every unchanged line to the older side, repeating until every line has an origin. Whitespace-only revisions can be skipped with the existing -w hunk set. Working-tree lines come from the current scanner.

What is new in the engine

  • pathHistory(ref, path) on ObjectDb: a commit walk with per-commit flattenTree lookups (memoised per commit today).
  • blame(ref, path): revision-pair diffs; reuse textDiff.ts.
  • A per-path cache in IndexedDB keyed by (commit oid, path) so the second look is instant.
  • isomorphic-git has no blame and no commit-graph support; both are own code. That is the same pattern as the index parser and worktree scanner.

How it works offline

The walk is a priority queue over commit dates starting from every ref head, exactly what git log --all does, paged 50 commits at a time. Lane assignment is the standard first-fit algorithm used by Git Graph and gitk. Per-commit stats come from a tree-to-tree diff of the commit against its first parent, already implemented in treeDiff.ts, computed lazily for visible rows the way file stats stream today.

Search over message, author and SHA is a substring match over the walked commits kept in memory; that is the entire scope of GitKraken's search.

What is new in the engine

  • walkCommits(from: Oid[], page) with a shared cache and abort signal (isomorphic-git 1.42 added abort support).
  • A commit-graph reader (tab 20) so the walk reads one static file instead of inflating every commit object: git reports 2–5× on linux-sized repositories.
  • Refs-by-commit index for the badges, from RefStore.
  • UI: a second sidebar mode, virtualised like the file tree.

The input returns File objects with relative paths. Repositories without a commit-graph file (git writes one on gc and, since 2.24, on fetch by default) get the naive path. The S2 real-repository checklist should record whether each has one.

Why not wasm-git (libgit2)

  • wasm-git 0.0.17 ships lg2.wasm at 0.82 MB (1.55 MB for the async build) plus glue; the whole diffgit main bundle is smaller than that.
  • It binds to Emscripten's in-memory or OPFS filesystem, not to File System Access handles: the entire .git would be copied into OPFS first. That breaks "read in place" and doubles disk use.
  • The sync build needs a worker with synchronous XHR; the async build pays the Asyncify penalty. Either way, a second engine to keep fixtures green against.
  • gitoxide has no browser target; its tracking issue names the blockers and is open.
  • What libgit2 would buy (blame, log speed) is ≈ 2 weeks of own code on the existing readers, with fixtures from real git as the oracle, the way the index parser and scanner were built.
