# T6.1 — Refresh scheduler

**Phase:** 6 · **Size:** M · **Depends on:** T3.5, T4.2 · **Blocks:** T6.2, T6.3, T6.4
**Plan refs:** §5.7, §6.1 refresh control

## Goal
One entry point for "something may have changed", with coalescing, cancellation of superseded work, mode reporting, and scope-aware invalidation.

## Deliverables
- `src/ui/refresh/scheduler.ts`:
  ```ts
  type RefreshReason = "manual" | "force" | "observer:git" | "observer:worktree" | "poll:git" | "poll:worktree" | "branch-change";
  interface Scheduler { request(reason: RefreshReason, paths?: string[]): void; setMode(mode: "live"|"polling"|"manual"): void; stop(): void }
  createScheduler(client: WorkerClient, store): Scheduler
  ```
- Behaviour:
  - Coalesce requests within 300 ms (trailing). Merge reasons: any `*:git` → `invalidate("refs")` + `reloadRefs()` before recompute (branch list/HEAD may change; if the checked-out branch changed, reset source to it per D5 default rule and keep target); `*:worktree` → `invalidate("worktree")`; `force` → `forceRehash()` + `invalidate("all")`.
  - Runs `computeDiff` with current `DiffSource`; superseded in-flight calls are cancelled by the engine (T3.5) and their `CANCELLED` rejections are swallowed here **only** (logged at debug level).
  - Updates `store.refresh` (`busy`, `lastAt`, `mode`, `lastError`).
  - Preserve UI state across recompute: active file, viewed marks (keys survive if oid unchanged), collapsed cards, scroll position (DiffPane handles restore).
  - After recompute, announce via `aria-live` (T5.6) "Diff updated".
- Wire `store.recompute` and the `R` shortcut / refresh button to `request("manual")`.

## Tests (vitest, fake timers, mock client)
Coalescing (5 requests → 1 compute), reason merging triggers `reloadRefs` only for git reasons, checked-out branch change resets source, superseded compute cancellation is silent while other errors surface as toast.

## Acceptance criteria
- [ ] Green; no other module calls `computeDiff` directly (grep guard).

## Amendments (review round 1) — T6.1 owns the refresh lifecycle
- **Ownership**: `createScheduler` starts and stops the observer (T6.2) and poller (T6.3). `closeRepo`/`openRepo` call `stop()` first; nothing else touches observer/poller lifetimes.
- **Degradation ladder**: `live` (observer) → `polling` → `manual`. Transitions: observer unavailable/errored/`disappeared` → polling with warning `REFRESH_DEGRADED`; poller gets `PERMISSION`/`HANDLE_GONE` → `manual` with **one** toast and a "Re-grant access" action (re-request permission from that click, then climb back up the ladder). No repeated toasts.
- **Debounce with max-wait**: trailing 300 ms, but never wait more than 2 s from the first request in a burst (a long `git checkout` otherwise starves refresh).
- **Config/ignore/attributes edits**: paths `.git/config`, `.git/info/exclude`, any `.gitignore`, any `.gitattributes` → `invalidate("all")` + `ignore.invalidate()` + `reloadRefs()`.
- **Invalidation is per-path**: for observer-reported worktree paths call `invalidatePath` (T1.1); only `force` uses `invalidateAll`.
- `HANDLE_GONE` during compute → stop everything, error screen (T4.3).
- Tests added: ladder transitions, single toast on repeated permission errors, max-wait, config-edit path invalidates ignore rules and refs.
